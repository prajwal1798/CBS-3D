# Case files

A CBS3D++ simulation is defined by a consistent set of files sharing one base name. The mesh alone is insufficient.

## Required files by simulation type

| Simulation | Required files |
|---|---|
| Non-dimensional fluid-only laminar | `.plt`, `.bco`, `.par` |
| Dimensional fluid-only laminar | `.plt`, `.bco`, `.par`, `.material`, `.matprop` |
| Spalart–Allmaras fluid case | `.plt`, `.bco`, `.par`, `.material`, `.matprop` |
| Conjugate heat transfer | `.plt`, `.bco`, `.par`, `.material`, `.matprop` |

All files must use the same base name:

```text
case_name.plt
case_name.bco
case_name.par
case_name.material
case_name.matprop
```

The solver argument is `case_name`, not an individual file.

## `.plt`: mesh and boundary faces

For the active CG/PETSc path, the header is:

```text
NELEM NPOIN NBOUN
```

It is followed by tetrahedral connectivity:

```text
element_id n1 n2 n3 n4
```

then node coordinates:

```text
node_id x y z
```

and boundary-face records:

```text
face_node_1 face_node_2 face_node_3 parent_tetrahedron raw_boundary_id
```

The parent-tetrahedron field is mandatory. It is used during preprocessing to determine the local face, geometry and outward normal.

### Mesh checks

- Node and element IDs must follow the indexing convention expected by the reader.
- Every boundary triangle must belong to a valid tetrahedron.
- Element connectivity must not contain repeated nodes.
- Tetrahedral Jacobians must be positive after applying the active orientation convention.
- The header counts must match the number of following records.

## `.bco`: boundary-ID mapping

The first line is:

```text
nflag mass_check
```

It is followed by one mapping for each raw boundary ID:

```text
raw_boundary_id solver_boundary_id
```

An identity map is valid when the Gmsh physical tags already equal the intended solver IDs:

```text
4 0
506 506
511 511
520 520
530 530
```

Every raw boundary ID referenced by `.plt` must appear in `.bco`.

## `.material`: element material assignment

This file is required when material properties are enabled. The first line is:

```text
NELEM
```

Each subsequent record is:

```text
element_id n1 n2 n3 n4 material_id
```

The element node order must exactly match `.plt`. A mismatch indicates that material IDs may be assigned to the wrong elements and must terminate the run.

Current phase convention:

```text
material_id = 0     fluid
material_id != 0    solid
```

Do not introduce an additional fluid material with a non-zero ID until phase classification is generalised in the implementation.

## `.matprop`: material properties

The material-property file defines the constant properties associated with each material ID. The active material reader expects positive density, heat capacity and thermal conductivity, with non-negative dynamic viscosity.

At minimum, verify:

```text
rho > 0
cp  > 0
k   > 0
mu >= 0
```

For Spalart–Allmaras cases, the fluid molecular kinematic viscosity is obtained from:

\[
\nu = \frac{\mu}{\rho}.
\]

A turbulence case therefore requires physical material data even when it contains no solid region.

The exact line grammar is controlled by the active `MeshIO` material reader and should be generated by the repository material-writing utility rather than edited manually for large cases.

## `.par`: run controls

The parameter file controls the active numerical and physical modes, including:

- dimensional or non-dimensional operation;
- steady/pseudo-time controls;
- pressure-solver selection;
- temperature/energy equation;
- material-property mode;
- turbulence activation and model selection;
- convergence limits and output frequency;
- boundary-condition values.

The parser is positional and historically compatible. Preserve labels, ordering and numeric blocks unless the reader is changed in the same commit.

### Optional depth-dependent volumetric heating (nuclear heating)

After the artificial-diffusion line (and before or after the optional
Spalart–Allmaras block) a block whose label contains `nuclear_heating` sets a
volumetric source that decays with depth from a plane, per material:

```text
Nuclear heating: nuclear_heating_on x0 y0 z0 nx ny nz nprofiles
1  0.0  0.28  0.0  0.0  -1.0  0.0  1
Nuclear heating profiles: material_id A_W_per_m3 lambda_m
1  1.6e6  0.15
```

\[
Q_e = A_m \exp\left(-\frac{d_e}{\lambda_m}\right), \qquad
d_e = \max\left(0, (\mathbf{x}_{c,e} - \mathbf{x}_0)\cdot\hat{\mathbf{n}}\right)
\]

with $\mathbf{x}_0$ any point on the first-wall plane, $\hat{\mathbf{n}}$ the
unit normal from that plane into the blanket and $\mathbf{x}_{c,e}$ the element
centroid. One data line per material; the value is stored in `Qvol_e` before
the time loop. A material with a profile must have `Qvol = 0` in the
`.matprop`, and a solid profile requires `source_solid = 0`. Every run with the
energy equation prints the whole-domain heat input, e.g.

```text
  HEAT INPUT (whole domain)
    nuclear heating, material 1 : A = 1.600000e+06 W/m3, lambda = 1.500000e-01 m, volume = ... m3, Q = ... W
    BC 532 surface flux : q = 1.000000e+05 W/m2, area = ... m2, Q = ... W
    HEAT_INPUT_TOTAL_W = ...
```

which `tools/energy_balance.py` compares with the heat carried out by the
coolant. Verified against the exact 1D solution in
`cases/nuclear_heating_slab` (serial and MPI agree to round-off).

Lines starting with `#` or `!` are comments anywhere in the `.par`.

### Required consistency

- A PETSc pressure-solver option requires a PETSc-enabled executable.
- Spalart–Allmaras requires dimensional material properties.
- Conjugate heat transfer requires consistent fluid/solid material IDs.
- Unsupported or dormant controls must not be presented as active capabilities.

## Gmsh pipeline

The intended pre-processing sequence is:

```text
.geo -> .msh -> .plt/.bco/.material/.matprop -> solver -> VTU/PVD
```

The exporter must preserve:

1. tetrahedral element connectivity;
2. node coordinates;
3. physical boundary tags;
4. boundary-triangle parent elements;
5. element material IDs.

Before running, inspect the exported boundary VTU in ParaView and colour by raw and mapped boundary IDs.

## Input audit checklist

- `.plt` header totals match the actual records.
- `.bco` maps every boundary tag used by `.plt`.
- Every boundary triangle has a valid parent tetrahedron.
- `.material` connectivity exactly matches `.plt`.
- Every material ID has a corresponding `.matprop` entry.
- Fluid properties produce the intended Reynolds number and viscosity.
- The executable supports the pressure-solver option selected in `.par`.
- All files share the same case base name.
